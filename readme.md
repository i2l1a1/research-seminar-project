# LLM Chain — REST-сервис API с многошаговой обработкой и оценкой ответов

Проект представляет собой REST-сервис, который принимает текстовый запрос пользователя и прогоняет его через
цепочку из 4 LLM-запросов (классификация вопроса → сбор фактов → генерация черновика → финальный
ответ → [дополнительно] оценка качества).

Основная цель — получить точные, безопасные и хорошо структурированные ответы, снизив галлюцинации и улучшив стиль с
помощью последовательных уточнений.

Сервис использует OpenRouter — единый унифицированный доступ к LLM (в MVP используются бесплатные модели
`google/gemma-4-31b-it:free`). Оркестрация этапов построена на LangChain, API реализован на FastAPI, всё
упаковано в Docker.

## Запросы к LLM (этапы генерации)

### 1. Классификация вопроса

Я выделил 5 типов запросов:

* **Technical** — технические вопросы или однозначные факты (код, даты, определения)
* **Advice** — выбор, сравнение, совет (нет единственно верного ответа)
* **Tutorial** — пошаговое объяснение, обучение
* **Current** — новости, будущее, актуальные данные (модель может не иметь актуальных данных)
* **Creative** — генерация идей или чего-либо творческого

### 2. Сбор фактов

LLM собирает и выписывает факты о вопросе, которые помогут LLM сформулировать максимально точный ответ на последующих
шагах.

### 3. Генерация черновика по фактам

LLM генерирует черновой ответ с опорой на факты (шаг 2).

### 4. Генерация финального ответа по фактам и черновику

Это финальный шаг. Тут LLM шлифует ответ: убеждается, что ответ написан на нужном языке, удаляет markdown, поправляет
формат ответа. Модель опирается на факты (шаг 2) и на черновик (шаг 3).

## Эндпоинты

- `POST /v1/generate` – основной эндпоинт. Возвращает финальный ответ, тайминги (общая задержка, задержка по шагам, тип
  вопроса) и оценки качества по 6 критериям.
- `GET /health` – проверка работоспособности сервиса.
- `GET /metrics` – метрики Prometheus.

## Запуск

### Инструкция по запуску

1. Создать файл `.env` на основе примера: `.env.example` и заполнить его нужными значениями для каждой переменной.
2. Запустить сервис через Docker Compose: `cd llm_chain_service && docker-compose up --build`. Сервис станет доступен на
   `http://localhost:8000`.
3. Открыть `http://localhost:8000/docs`.

## Архитектура проекта

Для просмотра архитектуры: `pnpx likec4 serve` (файл `architecture.c4`).

Самое важное:

- **REST API** – эндпоинты `/v1/generate`, `/health`, `/metrics`.
- **LangChain Pipeline Orchestrator** – последовательное выполнение 4 шагов.
- **OpenRouter Adapter** – HTTP-клиент для единообразного вызова LLM.
- **Логирование и метрики** – сбор latency, счётчиков, качества ответов.
- **Метрики и замеры на реальных запросах** – датасет, LLM-as-a-judge.
- **Масштабируемость (то есть на будущее)** – очередь задач (RabbitMQ/Redis) и кэширование ответов.

Слои: API слой (FastAPI), бизнес-логика (оркестратор LangChain), ML слой (вызовы OpenRouter), инфраструктурный слой (
логи, метрики, тесты, конфигурация).

## Метрики качества и производительности

### Релевантные метрики качества (LLM‑as‑a‑judge)

Оценка ответа производится отдельным LLM‑вызовом (шаг 5) по 6 критериям (каждый от 0 до 5, где 5 – идеально):

* `llm_answer_accuracy` – фактическая точность
* `llm_answer_relevance` – релевантность заданному вопросу
* `llm_answer_completeness` – полнота (охват всех аспектов вопроса)
* `llm_answer_conciseness` – краткость (отсутствие «воды» и повторов)
* `llm_answer_coherence` – логическая связность и структура
* `llm_answer_style` – стиль, грамматика, читаемость

### Тестирование

- **Unit-тесты** (pytest): 4 теста в `test_chain.py` + 3 в `test_api.py`.
- **Интеграционный тест** с реальным LLM.
- **Нагрузочный тест** (`tests/load_test.py`).

Запуск тестов:

## Формализация задачи и MVP

### Проблема

Одиночные LLM-вызовы часто дают либо довольно смелые, но содержащие галлюцинации ответы, либо осторожные и
поверхностные. Безопасность и стиль
трудно гарантировать одним промптом.

### Целевая аудитория

- Разработчики, встраивающие LLM в приложения, которым нужны надёжные, структурированные и безопасные ответы (например,
  для Q&A-сайтов в автоматической генерацией ответа).
- Люди, которые хотят получать точные и фактически корректные ответы, не разбираясь в prompt engineering.

### Пользовательские сценарии

1. Отправить текстовый запрос и получить финальный ответ.
2. Получить метаданные (задержки, тип вопроса).
3. Получить автоматическую оценку качества ответа (для отладки).

### Текущие ограничения

- Довольно долгое время ожидания (около 2 минут) из-за последовательных вызовов и бесплатных моделей.
- Отсутствует кэширование.

### MVP

**Что вошло в MVP:** REST API, цепочка из 4 LLM-вызовов, бесплатные модели, базовые промпты, метрики качества
и производительности, unit- и нагрузочные тесты.

**Что НЕ вошло и почему:** очередь (усложняет инфраструктуру), кэширование (не даёт значимого выигрыша
на MVP), платные/более быстрые модели (увеличивают стоимость проекта), графический интерфейс (дополнительная часть
проекта).

### Обоснование использования ML

Люди хотят получать корректные и относительно быстрые ответы, не прилагая значимых усилий, чтобы разобраться в теме.
Гуглёжка часто требует упорства и времени, поэтому для подобных запросов без LLM не обойтись.

### Обоснование выбора моделей

В MVP я использовал бесплатные модели `google/gemma-4-31b-it:free` – доступны без оплаты через OpenRouter и дают
приемлемое качество. Выбор моделей вынесен в конфиг, поэтому замена на платные не требует изменения кода.

### Риски проекта

- Зависимость от OpenRouter.
- Высокая стоимость при масштабировании (требует кэша и оптимизации промптов).

## User story

Как пользователь, я отправляю текстовый запрос в API и получаю качественный, полный и корректный ответ на свой запрос.
Кроме того, я могу посмотреть, сколько времени LLM потратила на генерацию, и другие метрики.
